# MoodFood

MoodFood is an Android application that provides personalized nutrition suggestions based on the user's current mood and wellness goals. It combines local mood tracking with AI-driven meal recommendations to support a healthier relationship between emotional state and diet.

## Features

- **Mood Tracking**: Log daily moods, symptoms, and notes to build a personal wellness history.
- **AI-Powered Meal Suggestions**: Receive meal recommendations generated by the OpenRouter AI API based on the current mood entry and user preferences.
- **Progress Tracking**: Review past mood entries and monitor wellness trends over time.
- **Analytics and Trends**: View detailed charts showing mood distribution and changes across configurable time ranges.
- **User Authentication**: Account creation and login using email and password, with security-question-based password recovery.
- **Onboarding**: Guided onboarding flow for new users covering app features and initial preferences.
- **User Preferences**: Customizable dietary preferences, cuisine types, and notification settings stored locally.
- **Offline-First Storage**: Room database persists mood entries and meal suggestions locally so the app remains functional without network access.
- **Mindfulness Content**: Supplementary mindfulness tips and breathing exercises accessible from the home screen.
- **Recipe Details**: Expanded view for suggested meals including ingredient lists and preparation notes.

## Architecture Overview

The application follows the MVVM (Model-View-ViewModel) architecture pattern:

- **Data layer** (`data/`): Contains repositories, Room DAOs, entities, and the Retrofit API client. Repositories are the single source of truth for each domain.
- **ViewModel layer**: Each major screen has a dedicated ViewModel that exposes state via `StateFlow` or `LiveData` and delegates business logic to the relevant repository.
- **UI layer** (`ui/`): Jetpack Compose screens observe ViewModel state and emit user events back to the ViewModel. Screens are organized into feature packages.
- **Navigation**: A single `AppNavHost` composable wires all screen routes together using typed `NavRoute` sealed classes.

## Setup Instructions

### 1. Clone the repository

```bash
git clone https://github.com/bhusallaxman22/moodfood.git
cd moodfood
```

### 2. Configure the API key

The project reads sensitive values from a `.env` file at the repository root. This file is listed in `.gitignore` and must never be committed.

```bash
cp .env.example .env
```

Open `.env` and replace the placeholder with your actual OpenRouter API key:

```
OPENROUTER_API_KEY=your-openrouter-api-key-here
```

See [Environment Variables](#environment-variables) for all available options.

### 3. Open in Android Studio

1. Open Android Studio and select **File > Open**.
2. Navigate to the cloned repository root and click **OK**.
3. Wait for Gradle to sync. If the sync fails, verify that the JDK version is 11 or higher under **File > Project Structure > SDK Location**.

### 4. Run the application

- Select a device or start an emulator from the **Device Manager**.
- Click **Run** (Shift+F10) or use the green play button in the toolbar.
- The app will build, install, and launch on the selected device.

### 5. Running tests

Unit tests are located in `app/src/test/` and instrumented tests in `app/src/androidTest/`.

```bash
# Unit tests
./gradlew test

# Instrumented tests (requires a connected device or emulator)
./gradlew connectedAndroidTest
```

## Environment Variables

The `.env` file at the project root is parsed by `app/build.gradle.kts` at build time and injected as `BuildConfig` fields. Values can alternatively be supplied via `gradle.properties`.

| Variable | Required | Default | Description |
|---|---|---|---|
| `OPENROUTER_API_KEY` | Yes | (none) | API key for the OpenRouter service |
| `OPENROUTER_MODEL` | No | `deepseek/deepseek-chat-v3.1` | Model identifier sent in API requests |
| `OPENROUTER_REFERER` | No | `https://moodfood.app` | HTTP Referer header sent in API requests |

Example `.env` file:

```env
OPENROUTER_API_KEY=sk-or-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
OPENROUTER_MODEL=deepseek/deepseek-chat-v3.1
OPENROUTER_REFERER=https://moodfood.app
```

At build time, these values are read in `app/build.gradle.kts` and exposed as:

```kotlin
BuildConfig.OPENROUTER_API_KEY
BuildConfig.OPENROUTER_MODEL
BuildConfig.OPENROUTER_REFERER
```

For CI/CD pipelines, set these as repository secrets and pass them as Gradle properties:

```bash
./gradlew assembleRelease \
  -POPENROUTER_API_KEY="$OPENROUTER_API_KEY" \
  -POPENROUTER_MODEL="$OPENROUTER_MODEL"
```

## Authentication and Security

MoodFood uses a custom email-and-password authentication system backed by the local Room database. No third-party authentication service is required at runtime.

Key security properties:

- Passwords are never stored in plain text. Each password is hashed using SHA-256 with a unique 16-byte cryptographically secure random salt. Note that SHA-256 is a general-purpose hash function and is faster than dedicated password hashing algorithms such as bcrypt, scrypt, or Argon2; upgrading to one of those algorithms is recommended before a production release.
- The stored format is `hash:salt` (both encoded as hex strings).
- Security question answers use the same hashing scheme (SHA-256 + unique salt) and are normalized to lowercase and trimmed before hashing to allow case-insensitive matching.
- All sensitive fields in `UserEntity` are nullable; no defaults leak information.

## Password Reset Flow

Users who forget their password can recover access through a three-step security question wizard:

1. **Email entry**: The user provides their registered email address. The app looks up the user and fetches their two security questions.
2. **Security question verification**: The user answers both security questions. Answers are normalized and compared against stored hashes. Both answers must be correct to proceed.
3. **New password**: The user enters and confirms a new password (minimum six characters). The password is hashed with a new salt and stored.

Security questions are set during account registration. Users choose two distinct questions from a predefined list and provide answers. Accounts created without security questions can still log in but cannot use the password reset flow.

## AI Integration

Meal suggestions are generated by sending a structured prompt to the OpenRouter API via a Retrofit client defined in `data/ai/OpenRouterApi.kt`. The prompt is constructed in the `prompt/` package and includes:

- The user's current mood and any noted symptoms.
- Dietary preferences from the user's profile.
- A request for structured meal recommendations (breakfast, lunch, dinner, and snacks).

The `SuggestionsRepository` sends the request, parses the response, and persists the returned suggestions to the Room database. Results are surfaced to the UI through the home screen ViewModel.

The AI model and API referer can be changed at build time via environment variables without modifying source code.

## Database

The app uses a single Room database (`AppDatabase`) with the following main tables:

| Table | Purpose |
|---|---|
| `users` | User accounts including hashed passwords and security question data |
| `mood_entries` | Individual mood log entries with timestamp, mood type, and notes |
| `suggestions` | AI-generated meal suggestions linked to mood entries |

The database version is managed in `AppDatabase.kt`. The current development build uses `fallbackToDestructiveMigration()`, which drops and recreates all tables whenever the schema version is incremented. This means existing data is lost on each schema update and is acceptable only during active development. Before publishing a production release, replace `fallbackToDestructiveMigration()` with explicit `Migration` objects that use `ALTER TABLE` statements to preserve user data across updates.
